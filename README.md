# Status vs Reality

A live London transport app: TfL's status for every Tube, Elizabeth line, Overground, DLR and tram line,
**checked against what's actually running**; live departures for any station or bus stop; every bus route
with its next buses stop by stop.
Built for passengers: one search box, mode tabs, saved favourites, plain words.

- **Live:** https://tfl-status-vs-reality.kelvinok52.workers.dev
- **Plan sent before coding:** [`docs/PLAN.md`](docs/PLAN.md) · **AI rules file:** [`CLAUDE.md`](CLAUDE.md) ·
  **Prompt sample:** [`PROMPTS.md`](PROMPTS.md)

## How it decides

For all 21 rail lines it compares the official status with live arrival predictions at two check stations
per line, against **that line's own timetable**. A line is flagged only when **both** stations agree.

| Verdict | When |
|---|---|
| **Worse than reported** | TfL says Good Service or Minor Delays, but gaps between trains exceed `max(2 × usual, usual + 5 min)` |
| **Status looks out of date** | TfL says Suspended or Severe Delays, but confirmed through-services run normally in every direction |
| **Matches** | Both stations agree with the status |
| **Mixed signals** | One station contradicts the status: too little to flag, so not called a match |
| **Can't verify** | Data missing, frozen, too short, or no timetable to compare against. It never guesses "OK" |
| **Closed** | Planned closure or outside timetable hours. Never a mismatch |

Each flag says what it saw and when, e.g. *"TfL says Good Service, but there's an 8-minute gap between
northbound trains at Tottenham Hale, starting in 12 minutes (usually 2)."* The live board underneath shows it.
Full rules: [`docs/SPEC.md`](docs/SPEC.md) §5. Every design decision has an ADR in [`docs/adr/`](docs/adr/).

## Architecture

```
Phone ──► static page (free, cached; service worker opens it offline)
     └──► Worker, one endpoint per screen, fetched when the screen is opened (ADR-011):
            /api/lines          home: statuses ──► D1 snapshot (≤ 30 s) ──► TfL (1–2 calls), one refresher
            /api/line/:id       one line's check + next trains ──► edge cache 30 s (served ≤ 90 s old, refreshed behind) ──► TfL (3 calls)
            /api/checks         every line's check, on request only; no button in the app (~42 calls)
            /api/station/:id    any station or bus stop ──► edge 30 s ──► TfL (1–4 calls)
            /api/bus/:route     status + next buses at every stop ──► edge 30 s ──► TfL (2 calls)
            /api/nearby?lat&lon the 5 closest bus stops with next buses ──► edge 30 s ──► TfL (≤ 6 calls)
            /api/search?q=      bus stop search ──► cached 1 h
            /api/index          station and bus route index ──► cached 1 day, no TfL call
          rules engine: pure function; timetables, station and route index generated by script (ADR-007)
```

- **Live, not polled** (ADR-001/011): TfL is called because someone opened that screen, at most every 30 s.
- **Survives outages** (ADR-002/006): the last good snapshot is served, marked stale, if TfL fails; the
  browser keeps its own copy for no signal; a 10 s back-off stops retry storms.
- **Survives repeats** (ADR-006): a D1 lease means one refresher; concurrent station requests share one fetch.
- **Shares a free Cloudflare account** (ADR-009): page loads are free; ≤ 2 D1 writes per refresh
  (≤ ~5,760/day worst case); the page polls every 60 s and stops after 10 min idle; a per-IP limit of 60 requests/min
  protects the TfL key (ADR-014).

## How it was verified

Details and dates: [`docs/verification.md`](docs/verification.md).

- **278 tests on every push** (GitHub Actions): every rule case in SPEC §7, the data layer's failure paths
  (TfL down, invalid body, partial failure, lease, D1 down), parsers against **real captured TfL responses**,
  the generated reference data, the free-tier bound (600 requests → ≤ 1 refresh per 30 s), and that the key
  never appears in a response, header, log or fixture. Plus typecheck, lint, bundle budget and gitleaks.
- **Against live TfL, by reading every verdict.** This changed the rules three times:
  - Ghost trains inside the live Bakerloo suspension → "running normally" needs confirmed through-services.
  - Trains inside the Lioness closure were shown as "Matches" → one disagreeing station is now "Mixed signals".
  - TfL's own `direction` mislabels Elizabeth line trains at Stratford → boards group by physical platform.
- **Production build** (measured at Phase 7, before the passenger-first redesign; not re-run since):
  - Lighthouse mobile: 92 / 100 / 100 / 100.
  - Load test: 101 req/s for 75 s, 0 errors, 4 refreshes. The load test found a stampede, which is now fixed.
  - Statuses match the tfl.gov.uk status page.

## What isn't finished

- **Buses** have stops near you, stop search, route status and live times, but aren't checked against live buses (no comparison
  rules for buses).
- **Elizabeth line and Overground are never flagged:** TfL has no timetables for them (404), so there's no
  "usual" gap. They can match or be "Can't verify". The **Cable Car** has no predictions at all: status only.
- **DLR** predictions reach only 2–13 min ahead, so it's mostly "Can't verify".
- **Thresholds** were tuned on one day (a Sunday); the Tram flag seen was marginal (9.01 vs 9 min).
- **Not checked:**
  - arrival times against tfl.gov.uk's own boards (statuses were compared with the site; the flagged
    Victoria gap was checked only against raw API arrivals);
  - the service worker's offline open in a real phone browser.
- **First visitor after 90 s idle** waits ~2 s for live statuses and ~1.3 s for a line (measured in dev); cached copies answer at once.
- **The home page shows mismatches only if a line was checked in the last 10 min** (someone opened it or
  ran a check on a line page); it no longer checks all lines in the background (ADR-011).
- **Abuse limits are partial:** the per-IP limit (ADR-014) is per Cloudflare location and eventually
  consistent, so many IPs together can still exhaust the TfL key.
- Night view says "Closed" but not "checks resume at HH:MM"; no history or trends.
- Reference data, the station index and bus routes are regenerated by hand (`bun run reference`).

## Run locally

Requires [Bun](https://bun.sh) 1.3+ and Node 22.12+.

```bash
bun install
cp .dev.vars.example .dev.vars   # add your TfL key (free at api-portal.tfl.gov.uk); gitignored
bun run dev                      # applies local D1 migrations, then starts Vite
```

Checks (same as CI): `bun run typecheck && bun run lint && bun run test && bun run build && bun run size`

Scripts:
- `bun run reference`: regenerate the timetables, station index and bus routes.
- `bun run fixtures`: re-capture test fixtures.
- `bun scripts/load.ts <url>`: run the load test.
- `bun run smoke <url>`: check the live API's response schemas.

## Deploy (manual; CI holds no Cloudflare credentials)

```bash
bunx wrangler login
bunx wrangler d1 create tfl-status-vs-reality --location weur   # once: near London, not near the deployer
#   then put the printed database_id into wrangler.jsonc
bunx wrangler secret put TFL_APP_KEY                            # once
bunx wrangler d1 migrations apply DB --remote
bun run deploy
bun run smoke https://tfl-status-vs-reality.kelvinok52.workers.dev
```
