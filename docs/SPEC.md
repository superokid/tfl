# Spec: TfL Status vs Reality

> Source of truth for behaviour. Reasons: [`adr/`](adr/). API facts: [`tfl-api-notes.md`](tfl-api-notes.md).
> If code and spec disagree, fix one in the same PR.

## 1. Goal

Show, in under a second on a phone, whether TfL's official line status matches what's really running.

Quality bar: correct on live data; survives outages and concurrent requests; tests on every push; no
keys in repo, logs, errors or browser; fast on a phone; real git history. A false "OK" is the worst
outcome, a false alarm the next worst.

## 2. Scope

- **Rail** (Tube, Elizabeth, DLR, Overground, Tram, Cable Car): checked on every refresh. Lines with no
  predictions (Cable Car) are status-only.
- **Any rail station and bus stop:** search and live departures ([ADR-008](adr/008-station-search.md), [ADR-011](adr/011-fetch-per-screen.md)).
- **Bus routes:** TfL status on demand; buses are not checked against live predictions.
- **Out:** history, map ([ADR-004](adr/004-text-list-no-map.md)), accounts, branch-only disruptions
  (known limit).
- Nothing the API provides is hardcoded ([ADR-005](adr/005-reference-data-from-api.md)). Exceptions go
  in `overrides.ts` with a reason, listed in the README.

## 3. Platform

- TypeScript, React + Vite, one Worker (static assets + API), one D1 (`weur`). No UI library.
- Bundle < 90 KB gzipped (raised from 80 KB on 2026-11-08: React alone is ~66 KB); app code (excluding React) < 20 KB. Reported in CI.

| Free-tier limit | Consequence |
|---|---|
| 50 subrequests, **D1 included** | ≤ 40 TfL + ≤ 6 D1 calls; use `db.batch()` |
| 6 connections waiting at once | Limiter of 6; timeout starts at send |
| 10 ms CPU (cron too) | Small payloads only |
| `waitUntil` ≤ 30 s | Refresh deadline 20 s |
| D1 100k writes/day | ≈ 18k/day worst case |
| TfL 500 req/min | 15 s freshness, lease, budget |

## 4. Data

### 4.1 Live data: per screen, on request ([ADR-011](adr/011-fetch-per-screen.md); SWR and lease: [ADR-006](adr/006-stale-while-revalidate-with-refresh-lease.md))

| Screen | Endpoint | TfL calls | Cache |
|---|---|---|---|
| Home | `/api/lines`: statuses (+ recent check verdicts) | 1–2 | D1 snapshot `lines` |
| Line | `/api/line/:id`: live check + next trains | check stops (+1 if the `lines` snapshot is > 90 s old, ADR-015) | edge 30 s; 30–90 s served, refreshed in background |
| Check every line | `/api/checks`: all verdicts, on request; no UI button | ~42 | D1 snapshot `checks` |
| Station / bus stop | `/api/station/:id` | 1–4 | edge 30 s |
| Bus route | `/api/bus/:route`: status + every stop with next buses | 2 (+2 stop order, cached a day) | edge 30 s |
| Bus stop search | `/api/search?q=` (≥ 3 chars) | 1 | edge 1 day |
| Bus stops near you | `/api/nearby?lat&lon` (rounded ~100 m, [ADR-012](adr/012-bus-stops-near-you.md)) | 1 (stop list, cached a day) + ≤ 5 | stop list 1 day; times share the 30 s station cache |

D1 snapshots: < 30 s fresh; 30–90 s served while the lease winner refreshes in `waitUntil`; > 90 s refreshed
inline. TfL down or invalid body → last good snapshot, `stale: true`, 10 s back-off. D1 down → direct
TfL call memoised per isolate. Edge-cached endpoints share one in-flight fetch and an in-memory limit
(60 calls/min per instance), and serve the last good copy stale on failure.

**Budget:** the D1 lease caps refreshes; one refresh makes ≤ 40 TfL calls, and the rest are marked
`budget` (`CANT_VERIFY`). On-demand endpoints share the per-instance limit above. The D1 per-minute
counter was dropped to save writes ([ADR-009](adr/009-free-tier-footprint.md), migration 0002).
On-demand endpoints (line, station, bus, search, nearby) are also limited to 60 requests/min per client IP
at each Cloudflare location. Over the limit → `429 rate_limited`, `Retry-After: 60`. A limiter error lets
the request through ([ADR-014](adr/014-per-ip-rate-limit.md)).

**Key:** `app_key` sits in the URL, so TfL URLs are secret. One helper builds them; one redacts them
before anything is logged, thrown or returned.

### 4.2 Storage ([ADR-002](adr/002-d1-snapshot-plus-browser-cache.md))

D1 snapshot (shared, outage fallback) · HTTP cache · `localStorage` (last good result) · service worker
(app shell only, never `/api/*`).

### 4.3 Reference data ([ADR-007](adr/007-generated-reference-data.md): generated by script, committed)

- `bun run reference` writes `src/shared/reference/rail.json` from the live API: lines, 2 check stations per
  line (route sequence; coverage weighted by route length, ≥ 2 stops from the ends where possible, spread
  apart), and per station × direction the departures timetable → service hours and hourly median gaps.
- Also learns platform compass word → direction from a sample of arrivals.
- TfL has no timetables for the Elizabeth line and Overground (404, even via its own disambiguation links):
  those lines use the per-mode fallback gap, so they can match or be "Can't verify", never flagged.
- `overrides.ts`: Cable Car is status-only (no predictions exist).
- Station index for search: `src/shared/reference/stations.json`, same script, with each station's position.

## 5. Rules

Pure function of (status, arrivals, reference data, `now`). No I/O, no `Date.now()`, `Europe/London`.
Code: `src/shared/rules/`. Input is the domain model in `types.ts`, not raw TfL JSON; parsing TfL into
it happens at the boundary (Phase 4), tested against real fixtures.
All numbers in `src/shared/config.ts`; tuning recorded in `docs/verification.md`.

### 5.1 Status → expected service (by description; every rail entry in `/Line/Meta/Severity` is covered)

| Expected | Descriptions |
|---|---|
| `NORMAL` | Good Service, No Issues, Information, No Step Free Access, Exit Only |
| `MINOR` | Minor Delays |
| `DEGRADED` | Severe Delays, Reduced Service, Change of Frequency, Issues Reported, Special Service |
| `PARTIAL` | Part Suspended, Part Closure, Part Closed, Diverted, Bus Service |
| `NONE` | Suspended, Not Running, No Service |
| `CLOSED` | Planned Closure, Service Closed, Closed |
| unknown | `CANT_VERIFY`, logged |

- Only statuses valid at `now` count, computed from the dates (`isNow` is unreliable).
- `PARTIAL` applies to its `affectedStops`; the other status applies elsewhere. Otherwise the most
  restrictive wins: `CLOSED` > `NONE` > `DEGRADED` > `MINOR` > `NORMAL`.

### 5.2 Definitions

- **Direction:** evaluated separately (`direction`, else `platformName`).
- **Predictions:** de-duplicated by vehicle. Gap checks count every prediction; "running normally" counts
  only confirmed (has a destination) services that don't terminate at the stop, and needs every direction
  usable (live ghost and boundary cases, see `tfl-api-notes.md`).
- **Prediction freshness:** If `timing.read` is > 3 min old, the feed is frozen and
  the direction is unusable.
- **Horizon:** the furthest prediction.
- **Window:** 30 min if normal gap ≤ 5 min, else 60 min, cut to the horizon.
- **Gap:** largest interval of now → first arrival and consecutive arrivals. Never after the last
  prediction.
- **Threshold:** `max(2 × normal, normal + 5 min)`.
- **Usable direction:** ≥ 1 prediction, and horizon ≥ 2 × normal or a gap over the threshold was seen.
  No predictions = unusable.
- **Day edges:** within 20 min of the first or last journey → `CANT_VERIFY`.
- **Also decided in Phase 2:**
  - Arrivals already due count as now.
  - If later arrivals exist beyond the window, the wait from the last in-window arrival to the window end
    counts as a gap.
  - A station in a `PARTIAL` status's affected stops is expected to have no service (`NONE`).
  - A direction with predictions but no timetable uses the per-mode fallback gap, with hours assumed open.

### 5.3 Verdicts

| Verdict | When |
|---|---|
| `HIDDEN_DISRUPTION` | Expected `NORMAL`/`MINOR`, and ≥ 2 stations have a usable direction over the threshold. |
| `STALE_ALERT` | Expected `NONE`, but ≥ 2 such stations have services within the threshold; or expected `DEGRADED`, but at ≥ 2 stations every gap is ≤ 1.5 × normal. |
| `MATCH` | ≥ 2 usable stations, and **every** usable station agrees with the status. One that contradicts it (too little to flag) → `CANT_VERIFY` (`mixed-evidence`). |
| `CANT_VERIFY` | Failed, invalid, empty or frozen data; < 2 usable stations; unknown status; `PARTIAL` with no affected stops or no check station in them; status-only line; budget hit; mismatch based on a fallback gap. |
| `CLOSED` | Expected `CLOSED`, or outside timetable hours. Never a mismatch. Reason `outside-hours` when every check direction is outside timetable hours, else `planned-closure`. |

- Ghost and boundary trains during a suspension: seen live in Phase 1 and ruled out (§5.2).
- Evidence: station, direction, normal gap (and whether it's a fallback), observed gap, horizon,
  time, and a sentence: *"TfL says Good Service, but the next southbound train at Euston is
  14 minutes away (usually 3)."*

## 6. UI ([ADR-011](adr/011-fetch-per-screen.md))

Passenger-first: "Is my line OK?" and "When's my next train or bus?"

- **Search** (top of every page): stations and bus routes from the index (no TfL call), bus stops from TfL
  (≥ 3 chars, 400 ms after typing). Stop results show "towards …".
- **Saved:** lines, stations, stops and routes as one-tap chips (device only).
- **Home:** mode tabs (Tube · Elizabeth line · Overground · DLR · Tram · Bus; they wrap, never hidden). Lines as
  TfL lists them: problems first, then A–Z; status in plain words with an icon, and TfL's reason (2 lines)
  under a line with a problem. Live-check note only when
  it adds something ("Live trains: longer waits than TfL says", "Live trains match"). Alerts on top for
  mismatches. "Lines near me" filters a rail tab to the lines at the closest stations, computed on the phone
  ([ADR-013](adr/013-rail-lines-near-you.md)).
- **Closed outside hours** (TfL says closed and the timetable has no service now, or TfL's message says
  "Service will resume"): routine, not a problem. Calm tone and ☾ icon, "Closed · opens about 05:30", sorted
  last, not counted in "N lines have problems". The time is TfL's if its message gives one, else the first
  timetabled train at the check stations; none if unknown or more than 12 h off when TfL says "later this
  morning". The line screen drops the "Live trains" card and shows each check station's first train.
- **Line:** TfL's status and message; "Live trains" card in plain words (why it couldn't check, if so); next
  trains at both check stations; "How we checked" evidence.
- **Station / bus stop:** each line's status with live departures by platform, 3 each ("More times" for
  the rest); bus stops show their flag letter and direction, and list routes with destination and next 3 times.
- **Bus tab:** saved stops and routes (search is the box at the top), then "Near you": the 5
  closest stops (letter, direction, distance) with the next buses per route, from "Use my location".
- **Bus route:** TfL's status and message, then a direction toggle and every stop in order with its next
  3 buses (stop letters as on the flag); tap a stop for its board. Not checked against live buses.
- States: loading skeleton, stale banner, device copy when offline, retry, "paused" after 10 min idle.
  A network error, timeout or 5xx is retried 3 times (2, 5, 15 s) with a "Trying again (n of 3)" note,
  then "Try again" is left to the user.
- AA contrast, colour never the only signal, 320 px. One light theme whatever the browser's setting. No TfL logo; "Powered by TfL Open Data".

### Free-tier footprint ([ADR-009](adr/009-free-tier-footprint.md))
Refresh ≤ every 30 s, 2 D1 writes each; station lookups cached 30 s with an in-memory limit; the client
polls every 60 s, never refetches within 30 s unless the user taps Refresh, and stops after 10 min idle.

## 7. Tests and CI

- **Fixtures:** trimmed live responses, from a capture script that never writes the key.
- **Rules:**
  - every verdict and every status mapping, unknown status, two statuses on one line
  - `isNow` wrong
  - frequent vs infrequent lines
  - horizon < window; now → first arrival as the gap
  - empty predictions at 1 vs 2 stations; frozen feed; Cable Car
  - Severe Delays with normal vs long gaps
  - night, day edges, non-operating day, planned closure, DST
  - Part Suspended with and without affected stops
  - fallback gap never gives a mismatch
- **Station selection:** branching lines use the shared section; interchanges preferred; ≤ 40 calls.
- **Data layer:**
  - fresh / recent / old snapshot
  - lease held
  - TfL down; partial failure; invalid body
  - call budget or on-demand limit hit
  - limiter ≤ 6 in flight
  - D1 down
  - invalid bus route
- **Secrets:** a refresh with a dummy key; the key appears in no body, header, log or error.
- **CI on every push and PR:** typecheck, lint, test, build + size, gitleaks.
- **Deploy** manually from a green `main`: `bun run deploy`, then `bun run smoke <url>`. CI never deploys
  and holds no Cloudflare credentials.
- **Live smoke test** every 6 h in CI, and by hand after each deploy: schema check of `/api/health`,
  `/api/lines` and `/api/line/victoria`.
